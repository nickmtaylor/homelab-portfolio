Understanding Your Homepage Dashboard

A study guide covering everything underneath the Homepage dashboard project (homelab/compose/homepage/ + homelab/appdata/homepage/) — the languages, the concepts, and the specific decisions made while building it — written so you can read the code yourself next time and actually know what you're looking at. It assumes zero prior knowledge of YAML, HTML, CSS, JavaScript, Docker, or networking, and builds everything up from there using your own project's real files as the examples.

Introduction

Everything in this dashboard is built from a small number of ideas repeated over and over. Once you can read:

  • a YAML file (used for Homepage's config and Docker Compose),
  • a bit of HTML/CSS (what the page looks like),
  • a bit of JavaScript (what happens after the page loads — fetching data, updating numbers, drawing charts),
  • and a Docker Compose file (what containers exist, how they talk to each other),

...you can read almost every file in this project. That's the goal of this guide: not to make you a professional web developer, but to get you fluent enough in each of these to open any file here, understand what it's doing and why, and make a confident change yourself.

Each section below uses real excerpts from your own project rather than made-up examples, and includes callout boxes like these:

Part 1 — The Web's Building Blocks

A web page is three separate layers stacked on top of each other, and keeping them mentally separate is the single most useful habit for reading any web project:

LayerJobQuestion it answers
HTMLStructureWhat elements exist on the page, and how are they nested?
CSSPresentationWhat do those elements look like — color, size, position?
JavaScriptBehaviorWhat happens — on click, on load, on a timer, on data arriving?

Your dashboard's page is mostly generated automatically by the Homepage application (written in a framework called React/Next.js, covered in Part 4). The parts you wrote by hand are appdata/custom.css (presentation) and appdata/custom.js (behavior) — Homepage loads both and lets them add to what it already built.

1.1 HTML — HyperText Markup Language

HTML describes structure using tags. A tag is a keyword in angle brackets, and most tags come in an opening/closing pair that wraps content:

<div>Hello</div>

This creates one element: a div (a generic container, no special meaning) containing the text "Hello". Tags can nest inside each other, which is what creates the DOM tree — "DOM" stands for Document Object Model, and it's just the name for "the tree of elements that currently makes up the page." Every element has exactly one parent (except the very top one) and can have any number of children:

<div id="system-panel">
  <div class="sys-inner">
    <div class="sys-stats">
      <div class="sys-stat">
        <span class="sys-value" id="sys-cpu">10.9%</span>
        <span class="sys-label">CPU</span>
      </div>
    </div>
  </div>
</div>

This is the actual shape of your System panel's CPU card. Reading it top to bottom: a div with id="system-panel" contains a div with class="sys-inner", which contains sys-stats, which contains one sys-stat per card, each holding a span for the number and one for the label.

Attributes

Inside the opening tag, name="value" pairs are attributes — extra information about that specific element. The two you'll see constantly:

  • class="..." — a label used to group elements for styling. Many elements can share the same class.
  • id="..." — a unique name for exactly one element on the page. Used both for styling a single specific thing, and for JavaScript to find it (document.getElementById('sys-cpu') — more in 1.3).
Gotcha

id must be unique on the page. If two elements share an id, document.getElementById() will only ever find the first one — this is a real, silent bug source, not a style preference.

Block vs. inline elements, and the tags that actually matter here

TagMeaningNotice
<div>Generic block containerNo meaning of its own — a box you style with CSS
<span>Generic inline containerSame idea as div, but doesn't force a line break — used for CPU's number vs. label so they sit side by side
<svg>Scalable Vector GraphicsDraws shapes with math instead of pixels — this is how the CPU sparkline and the storage donut chart are drawn (see 1.2/1.3)
<script>Runs JavaScriptHomepage uses this to load custom.js — see Part 4.3
<head> / <body>The two halves of every pagehead holds metadata (title, stylesheets, some scripts) that isn't itself visible; body holds everything you actually see
In this project

The question "why is the CPU/temp/weather panel showing up in <head> instead of <body>" from earlier in this project was really two separate things confused for one: the <script src="/api/config/custom.js"> tag that loads your code legitimately sits in <head> (Homepage puts it there), but the actual panel <div> your code builds is explicitly inserted into <body> (now, more precisely, into a scrolling container inside body — see Part 7.3). A script tag living in <head> says nothing about where the DOM it creates ends up.

1.2 CSS — Cascading Style Sheets

CSS answers "what does it look like." Every rule has the same shape:

selector {
  property: value;
  property: value;
}

The selector picks which element(s) the rule applies to. The declarations inside the braces set properties on those elements. Real example, from appdata/custom.css:

#system-panel .sys-value {
  font-family: var(--font-display);
  font-weight: 700;
  font-size: 26px;
  color: var(--text);
}

Selectors — how CSS finds elements

SelectorMatchesExample from this project
tagEvery element of that tagbody { ... }
.classnameEvery element with that class.service-card { ... }
#idThe one element with that id#system-panel { ... }
A B (space)Any B inside an A, at any depth#system-panel .sys-value — any element with class sys-value, anywhere inside the element with id system-panel
A > BAny B that is a direct child of A — not a grandchild#layout-groups > .services-group
A:nth-of-type(N)The Nth sibling of that tag inside its parent.services-group:nth-of-type(1) — the 1st group on the page
A[attr="value"]Elements with a specific attribute value#myTab button[aria-selected="true"] — the currently-active tab button
Debugging story

Early in this project, the section header colors weren't applying at all. The CSS used #services > .services-group:nth-of-type(N), but Homepage actually renders every group into a different container, #layout-groups, whenever that group has a layout: entry in settings.yaml (which yours all do). #services only holds groups with no layout entry — so the selector was silently matching nothing. The fix was purely about knowing which real container the actual HTML uses, which is why Part 4 exists in this guide: you can't get selectors right by guessing, you have to know the real structure.

Gotcha

The active-tab styling had the same kind of bug: the CSS looked for a class like .active, but Homepage marks the selected tab with the attribute aria-selected="true", not a class at all. aria-* attributes exist for accessibility (screen readers), but plenty of real apps piggyback on them as regular state markers too — always worth checking for when a class-based selector mysteriously matches nothing.

The cascade & specificity (why "cascading")

If two rules match the same element and set the same property, CSS needs a tiebreaker. Roughly, in order:

  1. Specificity — an id selector (#foo) beats a class selector (.foo), which beats a tag selector (div). More specific wins regardless of file order.
  2. !important — a declaration marked this way overrides normal specificity rules entirely.
  3. Source order — if specificity ties, whichever rule appears later in the CSS wins.
In this project

custom.css uses !important on the body rule (font, color, background) deliberately — Homepage's own built-in stylesheet also sets those properties, and without !important, whichever one happens to load second would win unpredictably. It's a blunt tool, appropriate here because you're deliberately overriding someone else's styles, not fighting your own.

The box model

Every element is a rectangle made of four nested layers, from the inside out: content, padding (space inside the border), border, and margin (space outside the border, between this element and its neighbors).

.sys-stat {
  padding: 12px 16px;      /* space inside the card, before the border */
  border: 1px solid var(--border);
  border-radius: 12px;     /* rounds the corners */
}

padding: 12px 16px is shorthand: two values means "top/bottom, then left/right." Four values (10px 20px 4px 24px) means top, right, bottom, left, clockwise from the top.

Flexbox — arranging things in a row or column

Flexbox is a layout mode for arranging a group of children along one axis, distributing space between them. You turn it on with display: flex on the parent, then control the children:

.sys-stat-plain {
  display: flex;
  flex-direction: column;  /* stack children vertically instead of side-by-side */
  gap: 4px;                 /* space between children */
  justify-content: center;  /* center along the main axis */
}

The default flex-direction is row (children side by side, left to right). Setting it to column stacks them top to bottom instead. This one property change is exactly what caused a real bug in this project:

Debugging story

Every section after the first used to collapse into a sliver at the top of the page. The cause: #layout-groups is a flex container that Homepage already sets to wrap rows (each service group claims a full row's width via its own style: row setting), but custom.css was forcing flex-direction: column on it. That flips which axis "full width" (flex-basis: 100%) applies to — from horizontal to vertical — so only the very first group ever got any space, and everything after it got squeezed to nothing. The fix was simply deleting the override; the default row behavior was already correct. Lesson: when you don't know why a container is arranged the way it is, don't assume — check what layout mode it's already using before adding your own.

Grid — arranging things in rows and columns

Grid is flexbox's two-dimensional sibling — instead of one line of items, you get an actual row/column layout. This is exactly how the five System-panel cards are laid out:

#system-panel .sys-stats {
  display: grid;
  grid-template-columns: repeat(5, minmax(0, 1fr));
  gap: 12px;
}

repeat(5, minmax(0, 1fr)) means "5 columns, each allowed to shrink to 0 but otherwise sharing the space equally" (fr = "fraction of the remaining space" — 1fr 1fr 1fr 1fr 1fr is the same thing written out). At narrower screen widths, media queries (below) switch this to fewer, wider columns so cards don't get crushed on a phone.

Media queries — different rules at different screen sizes

@media (max-width: 900px) {
  #system-panel .sys-stats { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

Everything inside @media (max-width: 900px) { ... } only applies when the browser's viewport is 900px wide or narrower. custom.css stacks three of these (1100px, 900px, 520px breakpoints) so the 5-column grid degrades to 3, then 2, then a single column as the screen shrinks — this is what "responsive design" means in practice: the same HTML, restyled at different widths, rather than separate mobile/desktop pages.

Custom properties (CSS variables)

:root {
  --bg: oklch(12% 0.01 260);
  --pos-1: oklch(68% 0.19 250); /* blue */
}
body {
  background-color: var(--bg) !important;
}

--name: value; defines a variable; var(--name) reads it back. Defining them once on :root (the <html> element — the outermost possible scope) means every color in the theme lives in exactly one place. Change --pos-1 once, and every blue accent across the whole dashboard updates together.

Why it matters

This is why the theme could be redesigned "from scratch" as a single coherent pass rather than hunting down every hardcoded color individually — the whole palette is ~10 variables, and everything else just references them.

oklch() — a more perceptually even color format

oklch(68% 0.19 250) describes a color with three numbers: Lightness (0–100%, how bright/dark), Chroma (0+, how saturated/vivid), and Hue (0–360°, the color wheel angle — 250° is blue, 70° is amber/orange, 300° is violet, 330° is magenta). It's a newer alternative to the more familiar rgb()/hex formats; its advantage is that bumping the Lightness number by, say, 10 actually looks like a consistent, equal jump in brightness across every hue — which made it much easier to keep the 4 section-accent colors (blue/amber/violet/magenta) feeling equally bright and equally saturated as a matched set, instead of eyeballing four unrelated hex codes.

Pseudo-classes: :hover, :nth-of-type()

A pseudo-class selects an element based on a state or position rather than an attribute:

.qs-item:hover { background: var(--surface-2) !important; }

This rule only applies while the mouse is actually over that element — CSS handles the "restore it when the mouse leaves" part automatically, no JavaScript needed.

1.3 JavaScript

Everything CSS/HTML can't do — reacting to events, fetching data over the network, drawing dynamic charts, running on a timer — is JavaScript's job. It's the only one of these three languages that actually runs (executes step by step); HTML and CSS just get read and displayed.

Variables

const METRICS_PORT = 9200;   // cannot be reassigned later
let selected = -1;          // can be reassigned

Modern JavaScript almost never uses the older var keyword. Use const by default; use let only for a value that's genuinely going to change (like a counter or a "currently selected" index).

Functions

function fmt(value, suffix = '') {
  return typeof value === 'number' ? `${value}${suffix}` : '—';
}

This reads: "define a function named fmt, taking a value and an optional suffix (defaulting to an empty string if not given). If value is a number, return it glued to the suffix; otherwise return an em-dash." The ? : is a ternary — a compact if/else that produces a value: condition ? valueIfTrue : valueIfFalse.

Template literals — backtick strings like `${value}${suffix}` — let you embed expressions directly inside a string using ${...}, instead of gluing pieces together with +. This project uses them constantly for building both text and HTML strings.

Arrow functions

const safe = (value) => String(value ?? '').replace(/[&<>'"]/g, c => ({...}[c]));

(params) => expression is a shorter way to write a function, common for small one-off functions passed to other functions (like the c => ... above, used inside .replace()). ?? is the "nullish coalescing" operator — a ?? b means "a, unless it's null/undefined, in which case b."

Objects, arrays, and JSON

const weather = { available: true, temp: 63, condition: 'Clear' };
weather.temp        // 63 — dot notation to read a property

const disks = [ { mount: '/mnt/volume1', percent: 62.8 } ];
disks[0].percent    // 62.8 — square brackets + index for arrays

An object is a set of named key/value pairs ({ key: value, ... }). An array is an ordered list ([item, item, ...]), indexed from 0. JSON (JavaScript Object Notation) is a text format for writing exactly this — every API response in this project (Glances, WUD, the two Python collectors) is JSON, which is why it looks identical to JavaScript object/array syntax; that's not a coincidence, JSON was modeled directly on it.

The DOM API — reading and changing the page from code

CallDoes
document.getElementById('sys-cpu')Finds the one element with that id
document.querySelector('.qs-input')Finds the first element matching a CSS selector
document.querySelectorAll('a[href]')Finds every matching element, as a list
document.createElement('div')Creates a brand-new element, not yet attached to the page
parent.appendChild(el)Attaches el as the parent's last child
parent.insertBefore(el, ref)Attaches el right before ref inside parent
el.textContent = '...'Sets an element's visible text (safely — special characters are shown literally, never run as HTML)
el.innerHTML = '...'Sets an element's contents by parsing a string as HTML — powerful, but only ever do this with content you trust
Gotcha

innerHTML and textContent look similar but are not interchangeable. textContent is always safe for untrusted text (user input, API data) because it never interprets its argument as markup. innerHTML parses its argument as real HTML — if that string ever contained something like <img onerror="..."></img> from an untrusted source, it would actually execute. This project uses innerHTML deliberately in a few places (building the panel's initial markup, injecting a generated SVG chart) because that content is entirely code-generated from numbers, never from unescaped external text — and uses textContent everywhere it's placing a value that ultimately came from an API response.

In this project

The quick-launch search palette's safe() function exists purely to make one specific innerHTML call safe: it HTML-escapes a service's name before dropping it into a template string, precisely because that name is read off the live page (via querySelectorAll) rather than typed by you — defense in depth, even though in practice it's your own Homepage content.

Events

trigger.addEventListener('click', open);
input.addEventListener('keydown', event => {
  if (event.key === 'Escape') close();
});

element.addEventListener('eventName', handlerFunction) says "run this function whenever this event happens on this element." Common events: click, keydown (a key was pressed — check which one via event.key), input (a text field's value changed).

Asynchronous code: Promises, async/await, and fetch()

Network requests take time and JavaScript doesn't want to freeze the whole page while waiting. A Promise is a placeholder for "a value that will exist eventually, or an error." async/await is syntax that lets you write code that waits for a promise as if it were a normal synchronous line, without actually blocking anything else on the page:

async function fetchJSON(path) {
  const response = await fetch(`${metricsBase()}${path}`, { cache: 'no-store' });
  if (!response.ok) throw new Error(String(response.status));
  return response.json();
}

fetch(url) starts an HTTP request and returns a promise for the response. await pauses this function (not the whole browser) until that promise resolves. response.ok is true for any 2xx HTTP status; anything else (404, 500, etc.) is treated as failure and an error is thrown deliberately, so the caller's try/catch can handle it. response.json() is itself asynchronous too (parsing the body takes a moment), hence a second await-worthy call — though here it's returned directly, and the caller awaits the whole function.

A function marked async always returns a promise, and any code that calls it typically needs its own await (or a .catch()) to deal with success/failure — this is why almost every function in custom.js's System panel section is async, all the way up.

Error handling: try/catch

try {
  const current = await fetchJSON('/system');
  // ...use it...
} catch (_) {
  // the collector is unreachable, or returned bad JSON — fail quietly
}

Code inside try { } runs normally; if any line inside it throws an error, execution immediately jumps to catch (error) { } instead of crashing the whole script. The (_) here is a deliberate convention for "we're catching this on purpose but don't need to inspect the error object" — an underscore as a variable name signals "intentionally unused" to anyone reading it later.

Closures & the IIFE pattern

(function () {
  'use strict';
  const METRICS_PORT = 9200;
  // ...everything in this file's second half lives in here...
})();

This shape — (function () { ... })() — is an Immediately-Invoked Function Expression (IIFE): a function defined and called in the same breath. The reason to bother: every const/let/function declared inside only exists inside that function — it can't collide with a variable of the same name declared by Homepage's own code, or by the other IIFE in the same file (the quick-launch search palette). Both halves of custom.js are wrapped this way specifically so they can't interfere with each other or with anything else on the page, even though they're loaded as one plain script with no module system.

setInterval — running something repeatedly

refresh();
setInterval(refresh, POLL_MS);

setInterval(fn, milliseconds) calls fn once immediately isn't quite right — it actually calls it every milliseconds, starting milliseconds from now, forever (until the page is closed/reloaded). That's why refresh() is always called once by itself right before setInterval(refresh, ...) is set up — otherwise the panel would show nothing at all for the first 10 seconds after the page loads.

Building SVG graphics from numbers

An SVG (from 1.1) is just XML/HTML-like markup describing shapes. A line chart is one <polyline> whose points attribute is a list of x,y coordinates:

`<svg viewBox="0 0 220 46" class="sys-chart"><polyline points="${coords}"/></svg>`

The actual work in sparkline() is arithmetic: take a list of raw values (e.g. CPU% samples), find their min/max, and rescale every value into the 0–46 pixel range available (this is called normalization) so the chart always fills its box regardless of whether CPU is hovering around 10% or spiking to 90%. The donut chart for storage works the same way in spirit but draws a circle's outline instead: an SVG <circle> can have its stroke drawn as a dashed pattern via stroke-dasharray, and by setting the dash length to exactly percent% of the circle's circumference, you get an arc that visually represents that percentage — with a second, full circle underneath in a muted color to show the "track" the arc sits on.

Part 2 — YAML & Configuration

Almost every file that configures something in this project — as opposed to files that are the running code — is YAML: services.yaml, settings.yaml, widgets.yaml, docker.yaml, bookmarks.yaml, and every docker-compose.yaml. It's worth genuinely mastering the syntax, because a single wrong space breaks the whole file.

2.1 YAML syntax

Key-value pairs

title: example.com

A colon followed by a space separates a key from its value. title:example.com (no space) is not valid — this is the single most common way to break a YAML file by hand.

Indentation is the entire structure

YAML has no braces or brackets for nesting — indentation is the only thing that expresses "this is inside that." From appdata/widgets.yaml (an earlier version, before it was emptied out):

- openmeteo:
    label: Home
    latitude: "39.xxxx"
    format:
      maximumFractionDigits: 0

label and latitude are indented under openmeteo:, meaning they are openmeteo's own settings. maximumFractionDigits is indented one level further under format:, meaning it belongs to format, which itself belongs to openmeteo. Indentation must be done with spaces, never tabs (most YAML parsers reject tabs outright), and the exact number of spaces doesn't matter as long as it's consistent at each level — 2 spaces per level is the convention used throughout this project.

Gotcha

Two sibling keys at the same logical level must start at the exact same column. If latitude were indented one space more or less than label, most parsers would either error outright or silently misinterpret the nesting — YAML has no redundancy to fall back on the way HTML's closing tags do.

Lists

cap_drop:
  - ALL

A leading - (dash, space) marks each item of a list. This is a list with one item, ALL. Lists can hold plain values (like this) or, as in the openmeteo example above, whole nested objects — - openmeteo: is "the first item of some list is an object with one key, openmeteo."

Compare the two styles used side-by-side in this project's compose files:

# "block style" — one item per line, used everywhere in this project
environment:
  - TZ=America/New_York
  - GLANCES_OPT=-w

# "flow style" — same meaning, all on one line, rarely used here
environment: [TZ=America/New_York, GLANCES_OPT=-w]

Strings: quoted vs. unquoted

Most plain text doesn't need quotes at all — title: example.com just works. Quotes become necessary when the value could otherwise be misread as something else:

SituationExample
Value starts with a special character ({, [, #, &, *...)latitude: "{{HOMEPAGE_VAR_WEATHER_LATITUDE}}"
Value could be misread as a number or booleanport: "8443" (if you specifically need it treated as text, not a number)
Value contains a colon-space, which would otherwise look like a new keylabel: "Home: upstairs"
Gotcha

Unquoted yes, no, true, false, on, off are all parsed as booleans by many YAML parsers, not as text — a classic trap if you ever wanted a literal string "no" as a value. Quote it if in doubt.

Comments

# Everything after a hash mark, to the end of the line, is ignored.
restart: unless-stopped  # can also trail after a real value

This project uses comments constantly and deliberately — nearly every non-obvious decision in every YAML file here (a removed directive, a chosen port, a security tradeoff) is explained inline, right where the choice was made, specifically so a future reader (including you, later) doesn't have to guess why something is the way it is.

Document markers

---
# https://gethomepage.dev/configs/info-widgets/
...

--- at the very top of a file marks the start of a YAML "document" — mostly a formality for a single-document file like these, but required by convention in a lot of tooling (and by Homepage's own examples), so this project follows it consistently.

2.2 Docker Compose YAML

First, the concepts underneath the file. A container is a lightweight, isolated way to run one program with its own filesystem and process space, without needing a full separate virtual machine. An image is the packaged, read-only template a container is started from (like nicolargo/glances:latest-full — a pre-built snapshot of "Glances plus everything it needs to run," downloaded from a registry rather than installed by hand). Docker Compose is a tool for describing a group of related containers — and how they connect to each other — in one YAML file, so you can start/stop/recreate the whole group with one command instead of many.

Anatomy of a service, using your Glances project

services:
  glances:
    image: nicolargo/glances:latest-full
    container_name: glances
    ports:
      - "127.0.0.1:61208:61208"
    environment:
      - TZ=America/New_York
      - GLANCES_OPT=-w
    volumes:
      - /volume1:/mnt/volume1:ro
    restart: unless-stopped
KeyMeaning
services:Top-level key — every container this file defines lives under here, one nested key per container.
image:Which pre-built image to run this container from.
container_name:A fixed name for this specific running container (otherwise Docker generates a random one) — needed anywhere another config file has to refer to this container by name (e.g. docker.yaml's my-docker connection targeting a specific host/port instead).
ports:Maps a port on the host machine (the NAS) to a port inside the container, as host:container. "127.0.0.1:61208:61208" means "only the NAS itself can reach this — not the LAN, not the internet" (see Part 3.4).
environment:Environment variables — named text values the program inside the container can read at startup, commonly used for settings and secrets instead of hardcoding them into the image.
volumes:Bind-mounts a path from the host filesystem into the container, as host_path:container_path[:mode]. /volume1:/mnt/volume1:ro makes the NAS's real storage pool visible inside the container at /mnt/volume1, read-only (ro) — the container can look at it but never modify or delete anything there.
restart:What to do if the container stops. unless-stopped means "always restart it automatically (e.g. after a NAS reboot), unless a human explicitly stopped it on purpose."

environment vs. env_file

environment:
  - METRICS_BIND=0.0.0.0        # fine as plain text — not a secret
env_file:
  - .env                        # WEATHER_LATITUDE/LONGITUDE live here instead

environment: writes values directly into the compose file itself. env_file: instead points at a separate file (conventionally named .env) full of KEY=value lines, and Docker Compose merges those in as if they'd been written under environment: directly. The entire reason this project keeps a separate .env per project (with a matching .env.example/.env.template containing only placeholders) is so real secrets and personal details (API keys, home coordinates) never have to sit in a file that gets freely copied, read, or shared — see the callout below.

Why it matters

This is also why compose/glances/.env.template exists with placeholder values like WEATHER_LATITUDE=changeme: it's safe to keep in version control / share / hand to an AI assistant, while the real .env (with your actual coordinates) only ever exists directly on the NAS, filled in by you.

network_mode: host vs. the default (bridge) networking

By default, every container gets its own private virtual network interface with its own IP address, and only the ports you explicitly publish (via ports:) are reachable from outside — this is bridge networking, Docker's default. network_mode: host instead gives the container direct access to the host machine's actual network — no translation layer, no need to publish ports individually, but also no isolation at all.

Why it matters

This project uses network_mode: host for most things (Homepage, WUD, system-metrics-collector) purely for simplicity/compatibility with this homelab's existing convention — but deliberately does not use it for docker-socket-proxy or glances, specifically because those two have real security surface worth isolating (one holds a path to the Docker API; the other's own web UI shows detailed process data) — for those, plain bridge networking plus a single explicit 127.0.0.1:PORT:PORT port mapping keeps them reachable only from the NAS itself, never the LAN.

Applying it inconsistently once (briefly hardening Glances the same way its own collector script is) was an actual mistake caught mid-project — see Part 7.1.

Part 3 — Networking & HTTP

3.1 Clients, servers, ports, and addresses

A server is just a program that sits and listens for incoming connections and responds to them. A client is a program that opens a connection to a server and asks it for something — your browser is a client; Homepage's container is a server (and, for some of its widgets, briefly a client too, when it fetches from Jellyfin/Home Assistant/etc. on your behalf).

Every server needs an address (which machine) and a port (which program on that machine — a single machine can run many servers at once, each listening on a different numbered "door," 0–65535). This project's addresses, in increasing order of how far they reach:

AddressReaches
127.0.0.1 ("localhost")Only the exact same machine making the request. A browser on your phone can never reach 127.0.0.1:9200 and mean the NAS — it always means "my own phone."
192.168.1.10Any device on the same local network (LAN) — your home Wi-Fi/ethernet, not the internet.
dash.example.comAnyone, anywhere on the internet who knows the domain — resolved to a real IP via DNS (3.2), then routed in from outside your home network.
Why it matters

This hierarchy is exactly why docker-socket-proxy and glances bind their ports to 127.0.0.1:PORT specifically — it's a deliberate statement that "only the NAS itself may ever connect to this," which rules out the entire LAN and internet at once, regardless of any firewall rule. It's also why the System panel's metrics collector binds to 0.0.0.0 (meaning "listen on every network interface, so anyone who can reach this machine at all can connect") instead — because unlike the other two, your own browser (on your phone, laptop, etc.) needs to reach it directly across the LAN, not just the NAS talking to itself.

3.2 DNS, reverse proxies, and TLS

DNS (Domain Name System) is the internet's phone book — it turns a name like example.com into an actual IP address. Cloudflare DDNS (Dynamic DNS) in this project's Infrastructure group exists because most home internet connections don't have a fixed IP — it periodically checks your home's current public IP and updates Cloudflare's DNS record to match, so the domain keeps pointing at the right place even after your ISP changes it.

A reverse proxy (Caddy, here) sits in front of your actual services and routes incoming requests to the right one based on the domain name requested — dash.example.com gets routed to Homepage's container, while a different subdomain gets routed elsewhere, all while only one thing (Caddy) is actually exposed to the internet. Caddy also does TLS termination: it's the thing that holds the actual HTTPS certificate and encrypts/decrypts traffic, so the containers behind it can speak plain unencrypted HTTP to each other on the trusted local side.

Basic auth is the simplest possible password-protection: the browser pops up a native username/password prompt before it'll let you through at all, enforced by Caddy before a request ever reaches Homepage. Homepage has no login system of its own, so this is the only thing stopping a stranger who discovers dash.example.com from seeing your dashboard.

3.3 The same-origin policy & CORS

An origin is the combination of protocol + domain/IP + port — http://192.168.1.10:3000 and http://192.168.1.10:9200 are different origins, purely because the port differs, even though it's the exact same machine. Browsers enforce a rule called the same-origin policy: JavaScript running on a page from one origin is not allowed to read the response of a request to a different origin, unless that other origin explicitly opts in.

That opt-in mechanism is CORS (Cross-Origin Resource Sharing): the server being requested adds a response header, Access-Control-Allow-Origin, saying who's allowed to read its responses.

Debugging story

The System panel worked perfectly when tested with curl from the NAS's own terminal, but showed nothing in the actual browser. The reason: curl is not a browser and doesn't enforce CORS at all — it happily reads any response. The dashboard page (port 3000) and the metrics collector (port 9200) are different origins to a browser, though, so fetch() inside custom.js was being silently blocked by the browser itself, even though the request reached the collector and got a perfectly good response. The fix was one line on the server side: self.send_header("Access-Control-Allow-Origin", "*") in system_metrics_collector.py. The lesson generalizes well beyond this project: whenever something works from a command line but not from a page in an actual browser, CORS is one of the first things to suspect — check the browser's DevTools Console (as you did) for a red "blocked by CORS policy" message, which says so explicitly.

Access-Control-Allow-Origin: * (a wildcard) means "anyone may read this." That's a reasonable choice here specifically because the data is read-only, non-secret, and already only reachable on your own LAN in the first place — a wildcard would be a much bigger deal on something that returns private data or accepts write requests.

3.4 Docker networking, and why docker-socket-proxy exists

The Docker socket (/var/run/docker.sock) is the actual control interface for Docker itself — anything that can talk to it can inspect, start, stop, or delete any container on the machine, and (because containers can mount arbitrary host paths) that's effectively equivalent to root access to the whole NAS. Homepage's container-status dots and WUD's update-checking both need some access to it, just to ask "what containers exist and what images are they running" — a much smaller ask than full control.

Debugging story

The first attempt to grant that narrow access was group_add: ["121"] — adding Homepage's container to the host's docker group (GID 121), the normal Linux way to grant access to a specific device file without full root. It didn't work; status dots stayed red. Tracing into Homepage's own startup script found exec su-exec ${PUID}:${PGID} "$@" — su-exec switches to the unprivileged user and drops every supplementary group in the process, wiping out the very group membership group_add had just granted. The real fix was architectural, not a permissions tweak: docker-socket-proxy is a small dedicated container that does hold the real socket, but exposes only a deliberately narrow HTTP API over it (POST=0 — no ability to create/modify anything; CONTAINERS=1, INFO=1, IMAGES=1, EVENTS=1 — read-only visibility only) on 127.0.0.1:2375. Homepage and WUD talk to that instead of the real socket, and never need any socket permissions of their own at all. This is a real instance of a broader security principle called defense in depth / least privilege: instead of granting a big capability and hoping nothing misuses it, build the smallest possible interface that does exactly the one thing you need, and grant access to that instead.

Part 4 — How Homepage Itself Works

Homepage is built with React (a JavaScript library for building user interfaces) and Next.js (a framework built on top of React that handles routing, server rendering, and project structure). You don't need to become a React developer to maintain this dashboard — but the next two ideas explain why a couple of real bugs in this project happened, and why custom.js is written the deliberate, careful way it is.

4.1 What React is actually doing

In plain HTML, the page is whatever you wrote, forever, until JavaScript explicitly changes it. React inverts this: you describe what the page should look like as a function of the current data ("if cpu_percent is 63, show '63%' here"), and React itself is responsible for figuring out what actually needs to change in the real DOM whenever that data changes — recalculating and re-rendering automatically rather than you writing manual "find this element, update its text" code for every single piece of data on the page. That's what all of Homepage's own live-updating widgets are doing under the hood; it's the same idea your hand-written refresh() function does manually and explicitly for the System panel, just automated at a much larger scale.

4.2 The Virtual DOM & reconciliation — why insertion point matters

To figure out what changed, React keeps its own private copy of "what the page should look like" (a lightweight in-memory tree, often called the Virtual DOM) and compares the new version against the previous one every time data changes. This comparison step is called reconciliation. When it finds a difference, it makes the smallest possible edit to the real DOM to match — it doesn't ever throw away and rebuild the whole page.

The catch: React only knows about elements it created. If you use plain JavaScript to shove a new element into the middle of a part of the page that React manages, React has no idea that element exists — and the next time React re-renders that exact area (because some state changed), it rebuilds that area from its own Virtual DOM, with no memory of your extra element ever being there. Depending on exactly where you inserted it, this can silently delete it, duplicate it, or in some cases throw an outright error.

Why it matters

This is the single biggest reason custom.js's System panel doesn't just get dropped in "wherever" — its insertion point was chosen specifically to sit outside any part of the tree React actually rebuilds when you switch tabs. Confirmed by reading Homepage's real source rather than guessing: clicking "Home"/"Media" only tears down and rebuilds a container called #layout-groups, deep inside a component called Home. Everything above that in the tree — including a wrapper div called #inner_wrapper — stays untouched across a tab switch. So inserting the panel as #inner_wrapper's first child is safe: React never reconciles that specific spot, so your manually-inserted element just... stays there, indefinitely, completely ignored by React and therefore never fought over.

Debugging story

An earlier version of the panel was inserted as document.body's first child instead of #inner_wrapper's. That's also safe from reconciliation, for the same reason — but it turned out to be the wrong parent for an unrelated reason: Homepage's actual page-scrolling happens inside #inner_wrapper specifically (it has overflow-auto set in CSS), while html/body/#__next are all just fixed at height: 100% with no scrolling of their own. A panel sitting as a sibling of #inner_wrapper, rather than inside it, sits outside that scrolling viewport entirely — so it stayed visually pinned at the top of the screen no matter how far down the page you scrolled. The fix and the original safety reasoning didn't conflict: moving one level deeper, to #inner_wrapper's first child, kept the exact same "outside anything React rebuilds" property while finally also being inside the actual scrolling area. The lesson: "is this DOM node safe from React" and "is this DOM node in the right visual position" are two separate questions, and you have to check Homepage's real source for both rather than assuming either.

4.3 How custom.css/custom.js actually get loaded

Homepage serves your two files back out through its own API at /api/config/custom.css and /api/config/custom.js (reading them off disk from wherever settings.yaml lives). custom.css is linked from inside Next's <Head> (a component that always places its children into the page's real <head>, regardless of where in the component tree it's written) — so a <link rel="stylesheet"> tag for it legitimately sits inside <head>. custom.js is loaded the same way, via <Script src="/api/config/custom.js" />, also inside a <Head> block on the actual page component. Neither of those facts says anything about where the content those files produce ends up — the stylesheet's rules apply wherever their selectors match (anywhere on the page), and the JavaScript's own code decides exactly where to insert its DOM (as covered in 4.2) — the loading location and the effect's location are two entirely separate things.

Part 5 — Just Enough Python

Two small backend programs in this project are written in Python: appdata/wud/collector/stacks_collector.py and appdata/glances/collector/system_metrics_collector.py. Neither needs any external libraries beyond what Python ships with (its "standard library") — a deliberate choice to keep them simple to deploy (nothing to install, just run the file).

5.1 Variables, dicts, and functions

GLANCES_URL = os.environ.get("GLANCES_URL", "http://127.0.0.1:61208").rstrip("/")

os.environ.get("NAME", "default") reads an environment variable (the same ones set in the compose file's environment:/env_file:) — Python's equivalent to JavaScript's fmt(value, suffix = '') default-parameter idea, just spelled differently. .rstrip("/") removes any trailing slash, so the rest of the code can safely glue on its own "/system" without ending up with an accidental double slash.

def pick_cpu_temp(sensors):
    for sensor in sensors or []:
        if isinstance(sensor, dict) and sensor.get("type") == "temperature_core":
            value = sensor.get("value")
            if isinstance(value, (int, float)):
                return float(value)
    return None

Python uses indentation itself to mark code blocks (no braces at all — even stricter than YAML about it). dict is Python's name for what JavaScript calls an object — key/value pairs, read with .get("key") (returns None, Python's version of undefined/null, if the key is missing, rather than crashing). isinstance(x, dict) checks the type of a value before trusting its shape — necessary here because this data ultimately came from across the network (Glances' API), and defensively assuming it might not look exactly as expected is good practice for any external input.

The full function reads: "go through every sensor reading; the first one whose type is specifically temperature_core (confirmed, by reading Glances' own source, to be the CPU-package sensor) — if its value is a real number, return it immediately. If nothing matched by the end, return None." or [] guards against sensors itself being None (e.g. if the API call failed) — looping over None directly would crash, looping over an empty list just does nothing, silently.

5.2 Threads and locks — why the collector scripts need both

Both collector scripts need to do two things "at once": continuously poll their upstream API in the background (Glances, or WUD) and answer incoming HTTP requests from your browser/dashboard immediately, without either one blocking the other. Python's Thread is how you run a second, independent stream of execution alongside the main one:

Thread(target=poll, daemon=True).start()
ThreadingHTTPServer((bind, port), Handler).serve_forever()

One thread runs poll() forever in the background (sleeping 10 seconds between each check); the main thread runs the actual web server, answering requests instantly with whatever the background thread most recently found — never making a visitor wait on a live Glances API call.

The danger with two threads is that they might both try to read and write the same shared variable (state) at the exact same instant, potentially catching it half-updated. A Lock prevents that:

with lock:
    state = { ... }

with lock: ... means "only one thread may be inside this block at a time — if another thread is already in here, wait your turn." Every place either thread reads or writes state is wrapped this way, guaranteeing the HTTP handler always sees either the fully-old or fully-new version of the data, never something in between.

5.3 Guided tour: system_metrics_collector.py

  1. Read config from the environment — GLANCES_URL, poll intervals, history buffer size, weather coordinates. All overridable, all with sane defaults, so the compose file only has to set what actually differs from the default.
  2. poll() — runs forever in a background thread. Each loop: call four Glances endpoints (/api/4/cpu, /mem, /fs, /sensors), pull out just the fields this project cares about, append the new CPU/temp reading onto a short rolling history list (trimmed to the last 12 samples — a 2-minute window at a 10-second poll rate), and store the whole snapshot in state under the lock. If anything throws (Glances unreachable, bad JSON, etc.), the except block marks available: False instead of crashing the whole thread — the loop always keeps running and keeps retrying every cycle.
  3. poll_weather() — the same shape, running as its own independent thread on its own, much slower interval (15 minutes, matching how often weather realistically changes), calling Open-Meteo's public API directly with coordinates that never leave this container.
  4. Handler — the actual HTTP server logic. Whichever path was requested (/system, /system/history, or /weather) determines which slice of the already-collected state/weather_state gets sent back as JSON. It never talks to Glances or Open-Meteo itself — it only ever reads what the background threads already gathered.
Why it matters

Notice the collector deliberately does not use Glances' own built-in /history endpoint. That was a real finding from reading Glances' actual plugin source code, not an assumption: Glances' history only tracks CPU's user/system sub-components, never the "total" percentage shown everywhere else, and its sensors plugin has no history support at all. Rather than accept that gap, this project keeps its own small ring buffer instead — a general pattern worth remembering: when someone else's API almost does what you need, check whether "almost" is actually good enough before building around its shape.

6.2 Data-flow walkthroughs

Loading the dashboard for the first time

  1. Your browser requests dash.example.com (or 192.168.1.10:3000 directly on the LAN).
  2. (Remote access only) Cloudflare DNS resolves the domain, Caddy receives the request, checks basic auth, and forwards it to Homepage's container.
  3. Homepage's Next.js server renders the initial page — reading services.yaml/settings.yaml/widgets.yaml to know what to draw — and sends back HTML plus links to its CSS/JS, including custom.css and custom.js.
  4. Your browser parses that HTML, requests custom.css and custom.js, and starts running React (this is "hydration" — attaching interactivity to already-rendered HTML).
  5. custom.js runs, builds the System panel's HTML by hand, and inserts it into #inner_wrapper.
  6. Homepage's own widgets (Jellyfin, Home Assistant, Uptime Kuma, etc.) each independently fetch their own live data from those services' APIs.
  7. custom.js makes its first calls to system_metrics_collector.py for /system, /system/history, and /weather, and starts its own repeating timers.

The CPU graph updating every 10 seconds

  1. In the background, on the NAS, system_metrics_collector.py's poll() thread wakes up, calls Glances, appends the new sample to its history list, sleeps again.
  2. Independently, in your browser, custom.js's setInterval(refresh, POLL_MS) fires, calls fetch() against /system and /system/history.
  3. The collector's HTTP handler answers instantly with whatever it currently has in memory — it never talks to Glances synchronously in response to your request.
  4. custom.js rebuilds the sparkline SVG from the returned numbers and swaps it into the page via innerHTML.

These two loops (the 10-second server-side poll, and the 10-second browser-side fetch) are independent and not perfectly synchronized — which is fine, because the server-side one is always slightly ahead, so the browser is always reading data that's already there rather than waiting on it.

Checking whether a container has an update available

  1. WUD, on its own schedule, asks docker-socket-proxy for the full list of running containers and their current images, then checks each image's tag against its registry.
  2. stacks_collector.py polls WUD's own /api/containers endpoint, groups the results by each container's Compose project name (the stack field), and serves a small JSON summary per project.
  3. Each Docker Stacks card in services.yaml is a customapi widget pointed at one specific project's URL on the collector — Homepage's server fetches that URL itself and renders the numbers into the card.

Part 7 — Debugging Case Studies

These are the same four incidents referenced earlier, collected here specifically as methodology — the transferable habits, not just "what the bug was."

7.1 The three-round "Invalid configuration file" saga

Deploying the Glances project through UGOS's Docker Compose GUI failed with a generic "Invalid configuration file" error — no line number, no key name, nothing. Three directives looked suspicious at once: pid: host, read_only: true + tmpfs:, and a volume mount of the bare host root (/:/rootfs:ro).

The approach: remove one suspicious directive, redeploy, see if the error changes. pid: host went first (it was untested anywhere else in the project) — same error. The hardening flags went second (also untested on a third-party image elsewhere) — same error. The bare-root volume mount went third — that cleared it.

Debugging story

The bare-root mount had actually been flagged as the most suspicious of the three from the very first message — every other volume mount anywhere else in this whole project targets a specific /volume1/... path, never the bare host root, so it stood out immediately as "the one thing that doesn't match this project's own established pattern." It still ended up tested last, purely because it felt like a bigger, more disruptive change to try first than the other two. That ordering cost two entire redeploy-and-wait cycles for nothing. The actual lesson: when several things are all equally untested, rank them by genuine suspicion (does this match what's already proven to work elsewhere?) and test the strongest suspect first — not whichever change is easiest to justify making, and not in the order you happened to think of them.

The general playbook this leaves you with for "no useful error message" situations: diff the failing config against something already known to work, list every genuinely new element, and test them in order of actual suspicion — one at a time, so you always know exactly which change fixed (or didn't fix) it.

7.2 The CORS bug

Covered in full in Part 3.3. The methodology point worth repeating here: curl succeeding is evidence the server works — it is not evidence the feature works, because a browser enforces rules curl doesn't. Whenever "it works from the command line but not in the actual page," check the browser's own DevTools Console before anything else; it will usually name the exact problem (as it did here, verbatim: "blocked by CORS policy").

7.3 The scroll-container bug

Covered in full in Part 4.2. The methodology point: this bug was reported by observation ("the bar doesn't move when I scroll") rather than by an error message — there was nothing to catch in a console. The fix came from reading Homepage's actual page-layout source code to find the real scrolling element (#inner_wrapper), rather than guessing at CSS tweaks that might have masked the symptom without addressing the actual cause. When the browser's own behavior seems to disagree with how you assumed the page was built, that assumption — not the browser — is usually what's wrong, and the fix is to go read the real structure rather than trial-and-error CSS.

7.4 The docker-socket permission saga

Covered in full in Part 3.4. The methodology point: the first fix (group_add) was reasonable and by-the-book — it's the textbook way to grant device access on Linux — and it still failed, because a layer underneath it (Homepage's own entrypoint script switching users) undid it. The fix required reading that entrypoint script directly rather than continuing to iterate on permission flags that all sat on the same side of the actual problem. Sometimes the correct fix isn't a variation on what you already tried — it's realizing the thing you're adjusting isn't the thing actually causing the behavior.

Part 8 — Debugging It Yourself Next Time

8.1 A general troubleshooting checklist

  1. Read the actual error message character by character before doing anything else — but also notice when it's not telling you anything (like UGOS's generic rejection), because that changes your strategy from "fix what it says" to "diff against something known-good."
  2. Reproduce the smallest version of the problem. A raw curl request bypasses the browser entirely — useful for isolating "is the server broken" from "is something about being in a browser breaking this" (exactly how the CORS bug was distinguished from a real server bug).
  3. Check the browser's own DevTools (Console tab for JS errors, Network tab for failed/blocked requests) before guessing at frontend bugs — the browser usually already knows exactly what went wrong and will say so.
  4. When a config file is silently ignored or rejected, diff it against a config that's already known to work in the same environment, and change one thing at a time.
  5. When your own mental model of how something works disagrees with its actual behavior, go find the real source (this project's own GitHub, Glances' plugin source, etc.) rather than iterating on guesses — every fix in Part 7 ultimately came from reading real source code, not from trial and error.
  6. Change one variable per test. Every multi-directive removal in the compose saga was still done one directive at a time, specifically so each redeploy's result was unambiguous.

8.2 Where to find ground truth for this specific project

QuestionWhere to actually check

"What fields does Glances' API actually return?"Glances' own plugin source, e.g. glances/plugins/cpu/__init__.py — the field names used in system_metrics_collector.py were all confirmed this way, not guessed from the docs alone.

Glossary

API (Application Programming Interface)
A defined way for one program to ask another program for data or to do something, usually over HTTP as JSON in this project.
Bind mount
Making a specific folder/file on the host machine visible inside a container at some path, via Compose's volumes:.
CORS (Cross-Origin Resource Sharing)
The mechanism a server uses to opt in to letting a browser page from a different origin read its responses. See Part 3.3.
DNS (Domain Name System)
Translates a domain name into the IP address to actually connect to.
DOM (Document Object Model)
The live tree of elements that currently makes up a web page, as the browser actually holds it in memory.
Docker Compose
A tool + YAML file format for defining and running a group of related containers together.
Environment variable
A named text value passed into a running program at startup, outside of any code/config file the program itself contains.
IIFE
Immediately-Invoked Function Expression — a function defined and called in one step, used to keep its variables private. See Part 1.3.
JSON
A text format for structured data (objects/arrays/strings/numbers), modeled on JavaScript's own object syntax.
LAN
Local Area Network — your home network, as opposed to the wider internet.
Origin
Protocol + domain/IP + port, taken together. Two URLs differing in any of those three are different origins to a browser.
PUID / PGID
The numeric user ID / group ID a containerized program should run as, matching a real user on the host so file ownership lines up correctly.
Reconciliation
React's process of comparing its previous and current in-memory view of the page and applying only the minimal real change needed. See Part 4.2.
Reverse proxy
A server that sits in front of other servers and routes incoming requests to the right one.
SSR (Server-Side Rendering)
Generating a page's initial HTML on the server, before it ever reaches the browser, rather than building it entirely with client-side JavaScript.
SVG
Scalable Vector Graphics — an XML-based format for describing shapes with math rather than a grid of pixels, embeddable directly in HTML.
TLS
Transport Layer Security — the encryption behind HTTPS.
YAML
A human-readable text format for structured configuration, using indentation to express nesting. See Part 2.1.
